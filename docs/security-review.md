## 4. Accepted risks and production prerequisites

1. **TLS 1.0/1.1 accepted on the default `*.cloudfront.net` names** — a consequence of running dev without
   `portalDomain`. Production config sets `portalDomain` + `hostedZoneId`; the CDK then enforces `TLS_V1_2_2021` and
   serves `data.<portalDomain>` (README N2). Dev keeps the defaults deliberately (no domain available). (S3 CORS is `*`
   in every environment by design since 2026-09-29 — item 13; `portalDomain` no longer narrows it.)
2. **MFA optional in dev** (`mfaMode: OPTIONAL`) so the e2e user can sign in unattended. Production: `REQUIRED`.
3. **CloudTrail S3 data events not enabled** — the trail records management events only. `GetDataAccess` (management)
   already ties every credential issue to user/org/download id; per-object `GetObject` events would add out-of-portal
   access detection at ≈ $0.10 per 100 k events (≈ 139 TB/month ≈ 10–20 k requests → cents). Decision deferred to
   T8.3/T8.4 with the cost review; S3 server access logs cover the same question at lower fidelity today.
4. **Browser-held credentials work outside the portal** (design §8) — inherent to Storage Browser; mitigations in
   place (prefix scope, 1 h, audit context, WAF rate limit, CloudTrail `GetDataAccess`).

## 5. Found during the review

- **Split engine hang on a failed write** (fixed, commit `2a33988`): a rejected `write()` left the File System Access
  writable in `ERRORED`; the engine's `close()` then threw out of `execute()`, so the record stayed `running` forever
  with no message (observed in the e2e run as 64 MiB / 12 GiB "진행 중" for 12 minutes). Now `close()` failures are
  tolerated, the progress rolls back to the session baseline (nothing was committed) and the row shows
  `paused / FILE_ERROR` with the browser's error. Regression test `splitEngine.test.ts`.
- Bucket policy lists `role/Admin` twice (it is both the uploader and the admin principal in dev) — cosmetic;
  IAM ignores duplicates.
- **AWS account id visible to end users** (2026-10-01): the Storage Browser locations table showed the data bucket name
  (`genome-portal-data-<account>-<region>`) to customer users. The column is now hidden (`withoutBucketColumn`). The id
  remains in the unauthenticated `config.json` (`accountId`, consumed by the Storage Browser adapter) and in the bucket
  name inside `listLocations` responses to signed-in users. An account id is not a secret and grants nothing by itself
  (all data access needs Cognito + Access Grants credentials), so this is accepted; a production deployment that wants
  it out of sight should set `dataBucketName` to a name without the account id.

## 6. Recommendations (non-blocking)

- **R1** Replace `cognito-idp:Admin*` on the admin role with the five actions the handlers call.
- **R2** Attach a rate-limit-only Web ACL to the web distribution before production (~$6/month); the API's own
  throttle (100 rps) is account-wide, not per client.
- **R3** Put `x-origin-verify` rotation on the runbook calendar (quarterly): new secret value → distribution custom
  header update → the Lambdas cache the secret in memory (`shared/originVerify.ts`), so the rotation completes on their next cold start; keep both values valid during the overlap by updating the distribution first.
- **R4** Enable CloudTrail S3 data events for the data bucket when moving to production (§4.3).
- **R5** Add a negative integration test that attempts `PutObject`/`DeleteObject` with credentials from `GetDataAccess` and expects `AccessDenied` (turns checklist item 6 from policy reading into measured evidence).
